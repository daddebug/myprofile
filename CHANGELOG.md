## 2026-08-08

### Fixed — Game Jam projects: missing covers, playable source, duplicated local builds (commit `12e7fdd`)

- `game-jam-8lzejf` ("Off Script | Game Jam") and `3d-vdr4qg` ("3D 温度感知解谜demo") were excluded from every publish since 2026-08-07 because their `PlayableGameTemplate` instance pointed at a local-only `/portfolio-assets/playable-games/...` build path — this, not a missing cover source, was the real cause of their covers appearing broken in production (both projects' real cover images already existed correctly in `content/projects/project-covers.json`, just never published).
- Added a `playUrl` field to `PlayableGameTemplate` (`src/templates/PlayableGameTemplate.tsx`) so a Playable Game entry can reference an externally-hosted build instead of a local one. Both projects now use it, pointing at their canonical Unity Play builds (confirmed against `src/data/publishedPortfolio.json` project/build-name metadata before writing, not guessed): `game-jam-8lzejf` → `https://play.unity.com/en/games/877cb160-3478-4f23-bf1d-384942b132f1/gamescript`, `3d-vdr4qg` → `https://play.unity.com/en/games/d21db0be-36a7-4193-a21f-64e34a979196/tem`. Unity Play was empirically confirmed (real iframe test, not just header inspection) not to support reliable iframe embedding, so both render their existing cover with a "打开游戏 / Play Game" external-tab link rather than an embed — this also structurally rules out the recursive "portfolio inside portfolio" iframe bug, since no URL is ever assigned to an iframe `src`.
- Closed a real "registered but never collected" gap: implemented the previously-missing `playable-game-covers` export/import path (`src/lib/portfolioContentClient.ts`, `scripts/portfolioContentPlugin.ts`, `src/lib/productionBundleExport.ts`, `scripts/import-production-bundle.mjs`), mirroring the existing `project-covers-disk` pattern, so each project's Playable Game cover now actually publishes.
- Fixed the publishing preflight (`scripts/publishing-preflight-lib.mjs`) to stop requiring a collected local build for a game reference that carries `playUrl` — previously any `gameId`-keyed field unconditionally required a `playable-game-builds` asset, which no longer existed once the local build was retired.
- Retired the two now-superseded local WebGL builds (`game-jam-8lzejf`'s ~104 MiB "gamescript" build, `3d-vdr4qg`'s "afterwarm" build) plus a third, fully orphaned build (`from-theme-to-playable-rule`, ~667 MiB, zero live references) discovered during the same pass — none tracked by git (`content/`, `public/portfolio-assets/` are git-ignored), so deletion had zero git-diff impact and freed roughly 1.53 GB of local disk.
- Verified: `pnpm typecheck`/`pnpm build` pass; a real dry-run preflight+import against a fresh browser export reported 0 errors; the confirmed import (`portfolio:import -- --confirm`) and a scoped commit/push landed as `12e7fdd`. **Verified live on production** (`https://myprofile-teal.vercel.app`, the correct deployment — `myprofile.vercel.app` is an unrelated third party's site, do not use it): both project pages show their real cover on the project overview carousel and project page, no X/placeholder, the "打开游戏 / Play Game" link's `href` matches the exact expected Unity Play URL for each project, no iframe/recursion, no console errors.

### Fixed — production project covers

- Root cause: `src/lib/productionBundleExport.ts` only ever collected covers from the `project-covers-indexeddb` IndexedDB store, which has had zero writers since `ProjectCoverEditor.tsx` moved to saving covers on disk (`content/projects/project-covers.json`, the `project-covers-disk` adapter). The registry and `import-production-bundle.mjs` already supported that adapter; nothing in the exporter ever collected from it — a registered adapter with no real collector behind it. Added a collector that fetches each canonical project's real disk cover through the same `/__portfolio-content/project-covers/resolve` endpoint the live site's own `useProjectCover()` hook already uses in DEV, tagged `sourceAdapterId: "project-covers-disk"`.
- Also fixed a `publishing-preflight-lib.mjs` classification gap this surfaced: `PlayableGameTemplate`'s embedded cover field shape (`{coverId, publicUrl}`) hit a generic "unregistered adapter" error for its `publicUrl` key instead of being attributed to the already-registered `playable-game-covers` adapter (the existing code only recognized the reverse key order, `coverId` with a `publicUrl` companion, not `publicUrl` with a `coverId` companion).
- Added an explicit, CLI-visible `--exclude-project=<id>[,<id>...]` flag to `import-production-bundle.mjs` (never a silent default) to publish around an unrelated, already-known blocker: `game-jam-8lzejf` and `3d-vdr4qg` have Playable Game covers/builds still pointing at local-only `/portfolio-assets/playable-games/...` paths (the pre-existing, separately-tracked production-hosting gap). Excluded projects' existing published state is read back from the current `publishedPortfolio.json` and merged into the output unchanged, and excluded from the rewrite-validation preflight (so legitimately-pre-existing bad references in untouched legacy data aren't re-flagged) — verified this does not affect the pass/fail correctness of that check for the projects actually being published.
- Verified: real export → dry-run → confirmed import (commit `8a57564`, pushed, Vercel deployed) → live production check in the owner's real Chrome. All 5 configured project covers (`ui-personal-practice`, `interaction-intelligence-system`, `ai-assisted-ui-environment-design`, `ui-16ienxj`, `project-1ua2677`) serve from `/images/published/covers/<id>.<ext>` at HTTP 200 with correct `image/*` content-type, decode with positive `naturalWidth`/`naturalHeight`, and are visibly rendered on the live homepage's featured-project cards. Zero `/portfolio-assets/`, `blob:`, or dev-only references remain in the published cover paths. Ran the full registered publishing-completeness check (all 16 source families) against the post-import state: `ok: true`, 0 issues.
