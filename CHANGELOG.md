### Added — Collection PDF size optimization: 87.76MB → 5.47MB (93.8% reduction), no Smallpdf needed

- **Root cause (audited first, per explicit instruction)**: 99.3% of the original PDF's size was image bytes — Chromium's `page.pdf()` always embeds a raster `<img>` at its full natural/decoded resolution as raw, unfiltered `/FlateDecode` samples, regardless of on-page CSS display size, and never preserves a source JPEG's own encoding. Dozens of images were embedded at 200-780 effective DPI relative to their real display size (e.g. a 2000×2000px/5.55MB image displayed at 281 CSS px wide).
- **Stage 1 — upstream fix**: `scripts/exportImageResize.ts` (new) runs inside `page.evaluate()`, only inside the disposable Playwright capture tab, right before `page.pdf()` — walks `document.images`, and for any image whose natural resolution meaningfully exceeds its real `getBoundingClientRect()` CSS size (×2 retina headroom), redraws it into an offscreen canvas at the capped size (aspect ratio preserved), pins the element's CSS box inline first so layout can't shift, and swaps `img.src`. Wired into both capture sites: `createExactWebPdf` (`scripts/exactWebExportPlugin.ts`) and `renderSectionPdf` (`scripts/portfolioCollectionExportPlugin.ts`). Needs no image-type classification or per-project rules. Verified: 87.76MB → 26.41MB (69.9% reduction) alone.
- **Stage 2 — narrow final encoding pass**: `scripts/pdfStreamEncodingOptimizer.ts` (new, called from `mergeCollection` right after the canonical merge produces literal bytes) closes the remaining gap, which is a pure Chromium encoding-efficiency limitation (still 100% raw `FlateDecode` after Stage 1, not an oversizing problem). Its rule was reverse-engineered from a real Smallpdf-compressed reference export of this same portfolio (user-supplied, ~4.1MB, inspected object-by-object via `pdf-lib`, including tracing one object's reachability through a page-level luminosity soft-mask's `ExtGState /SMask /G` to confirm it wasn't orphaned): every image WITHOUT its own `/SMask` gets a fixed-quality-70 DCTDecode/JPEG re-encode, kept only if genuinely smaller than a real PNG-style-predictor lossless re-filter computed alongside it (own from-scratch byte-level implementation — adaptive per-row filter selection, then deflate — chosen specifically to avoid trusting an external encoder's color-mode behavior); every image WITH its own `/SMask` (and that SMask's own object) always stays on the lossless path. Every lossless candidate is decoded back and verified byte-for-byte identical before use; every JPEG candidate is decoded back and dimension-checked. Also deduplicates byte-identical image objects (rewrites every reference to one survivor via a generic object-graph walk, then deletes the dead copy — reassigning what a ref points to doesn't save bytes unless every reference to the old object number is repointed first) and saves with `useObjectStreams` enabled.
- **Verified end to end through the live `/export` UI** on the real 3-project Collection (interaction-intelligence-system, ai-assisted-ui-environment-design, 3d-vdr4qg): final size 5,732,450 bytes (5.47MB); 61 of 125 images recompressed (47 as JPEG, 14 lossless-predictor), 10 duplicate objects removed. Page count (4), page dimensions, and cover-tab link annotations byte-identical to the pre-fix baseline (`pdf-lib` structural diff). All 4 pages visually inspected at both normal and 200dpi zoom: cover gradients still banding-free (the real-size comparison naturally keeps smooth gradients on the lossless path), dense UI-screenshot text still sharp under close zoom, 3D scene renders and alpha-having graphics unchanged, no white blocks or missing images.
- An earlier exploratory approach (rewriting an already-generated PDF's image objects with a guessed content-type classifier) was tried first, hit a real corruption bug (sharp's PNG encoder silently switching to indexed/palette output for low-color-count images), and was abandoned once the user redirected to fixing the actual upstream cause instead — kept only as clearly-marked EXPERIMENTAL/UNUSED reference (`scripts/pdfImageOptimizer.mjs`, `scripts/pdfSizeOptimizeCli.mjs`), not wired into any live pipeline.
- New permanent rule recorded in `CLAUDE.md`, `skills/safe-project-editing/SKILL.md`, and `skills/portfolio-collection/SKILL.md`: fix upstream root causes, not downstream symptoms — plus an explicit "allowed scope" note in the Collection skill limiting the final PDF-level pass to generic image-encoding optimization for Chromium's own limitation, never repair of upstream sizing/rendering problems.
