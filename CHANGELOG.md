## 2026-09-19 - InlineLayoutTextField: an authored Enter now survives as a real "\n" (was silently collapsing)

Fixed multiline `InlineLayoutTextField` (`src/components/template-tools/InlineLayoutTextField.tsx`) losing an authored hard line break: pressing Enter visually looked like a new line while editing, but the stored/rendered value collapsed back to continuous text on blur/reload. Not committed, pushed, deployed, or published.

- **Root cause (confirmed, matches the reported hint)**: `commit()` read the contentEditable's value via `el.textContent`, which concatenates every text node with no separator -- so whatever block structure the browser's own native Enter behavior inserted (a new `<div>`, in Chromium) at the caret was silently discarded on read. Even if it had survived, there was no `white-space: pre-line` anywhere for this primitive, so an embedded `\n` character would have been collapsed away by the default `white-space: normal` regardless.
- **Read side**: `commit()` now reads `el.innerText` (not `textContent`), normalized with `.replace(/\r\n?/g, "\n")` -- `innerText` represents a block-structure line break as `"\n"`, which `textContent` never did.
- **Write side**: `el.textContent = value` (the external-value resync effect) is unchanged -- a string containing `"\n"` written this way is fine once the CSS renders it as a break (see below).
- **Enter handling for multiline fields**: pressing Enter now inserts a literal `"\n"` character directly into the current text node at the caret (`Text.insertData`), instead of letting the browser create its own block element. Two other techniques were tried first and both failed under live verification: `document.execCommand("insertText", false, "\n")` silently no-ops when called from inside a real keydown handler in this environment (confirmed working only from a detached script context, not from the actual event path); `Range.insertNode()` for a collapsed caret splits the text node and leaves the caret in an element/child-index Range shape that behaved inconsistently with further input. `Text.insertData()` mutates the existing text node in place and leaves the caret at a plain `(textNode, offset)` position -- the same shape ordinary typing itself already produces -- with a fallback to inserting a fresh text node only when the caret isn't already inside one (e.g. a still-empty field). `commit()` is called directly afterward since none of this dispatches its own `input` event. Single-line fields are unaffected -- Enter still just blurs. Shift+Enter is intentionally not distinguished from a plain Enter (no existing distinction to preserve).
- **Rendering**: added `[data-multiline="true"] { white-space: pre-line; }` to `inline-layout-text-field.css` (the primitive's own generic stylesheet, not a per-field override) -- renders an authored `"\n"` as a real line break while still collapsing/wrapping ordinary whitespace normally. Not `white-space: normal` (would swallow the break again) and not `pre`/`pre-wrap` (would also stop wrapping or start preserving incidental double-spaces). `data-multiline` is now set on both the editable and read-only render paths (previously only `aria-multiline` existed, and only on the editable path), so Editing Mode OFF renders the same break as Editing Mode ON. `.home-v2__long-text` already had its own `white-space: pre-wrap` from earlier work -- left untouched; a `pre-wrap` field already handles `"\n"` correctly regardless of which rule wins the cascade, so there's no conflict.
- **IME/composition and caret preservation**: the composition guard (`isComposingRef`, `onCompositionStart`/`onCompositionEnd`) was not touched -- the new Enter handling shares the same `isComposingRef.current` early-return the old single-line-only Enter handling already used, so an IME's own Enter-to-confirm keystroke is untouched by this change. Not live-verified with a real Chinese IME (this environment's automation cannot drive genuine OS-level composition), but the guard is structurally unchanged, not new.

### Added — Collection PDF size optimization: 87.76MB → 5.47MB (93.8% reduction), no Smallpdf needed

Wired into both capture sites: `createExactWebPdf` (`scripts/exactWebExportPlugin.ts`) and `renderSectionPdf` (`scripts/portfolioCollectionExportPlugin.ts`). Needs no image-type classification or per-project rules. Verified: 87.76MB → 26.41MB (69.9% reduction) alone.
