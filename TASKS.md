The same constraint now also applies to a future DILIDA DESK `COLLECTION PDF` action against `docs/PDF_EXPORT_ARCHITECTURE.md`'s workflow — not implemented yet.
- **PDF viewer performance still unverified.** Not measured against a real generated PDF since the architecture/registry work landed.
- **Project trailing blank space still unverified.** `scripts/pdf-export-postflight-lib.mjs`'s project blank-tail rule now exists to check this automatically, but has not yet been run against a real regenerated Collection PDF.
- **TOC horizontal safe margins still unverified.** The registry's `toc.note` and the postflight's TOC safe-area check both flag the same specific, not-yet-confirmed risk: a full 7-slot TOC grid's worst-case label extent computes to ~198px past the safe-right edge. A real 4-entry TOC (the current `MAX_COLLECTION_PROJECTS` cap) looked visually balanced in the 2026-08-07 emergency-export screenshot, but the 7-slot worst case is still unverified.
- **Project-page blank-segment pagination bug: real root cause still unknown; only stopgaps are in place.** An explicit, opt-in-only `?emergencyPdfExport=1` override on `/export` now exists (`isEmergencyPdfExport()` in `src/lib/portfolioCollectionExport.ts`, threaded to `captureProjectPage` in `scripts/portfolioCollectionExportPlugin.ts`): when a segment-count mismatch still occurs even with `maxSegmentHeightPx=16000` (real repro 2026-08-07: `project-1ua2677` "2 segments for 1 planned" on a later run), it keeps every generated segment instead of failing, embedding any segment beyond the planned count at its own full native height instead of cropping — verified in a real regenerated PDF, no clipping. Every other blocking check (missing draft, missing images, clipped content, failed rendering, empty body, template overflow) is untouched and still throws normally with or without the flag. Normal production exports never set this param. Real repro this session: `project-1ua2677` produced 4 physical PDF segments for 3 planned slices, then (with all projects selected) `interaction-intelligence-system` produced 5 for 4 — confirming this is systemic, not project-specific, and not caused by the `data-project-print`-scoped `figure/table/img` rule previously suspected (that attribute is provably never set during collection capture — its only setter is the owner-only manual print button, gated on a `?printProject=1` query param the collection pipeline never sends). Two CSS-only fixes were tried and both reproduced the identical failure: (a) forcing `break-inside: auto` on figure/table/img under `data-collection-export-capture`, (b) restoring `break-inside: avoid` on every top-level `[data-template-instance-id]`/`[data-document-section]` module (both since reverted/superseded — see `src/styles.css`, "EMERGENCY FIX" comment near `maxSegmentHeightPx`). This means **break-inside CSS is not the actual lever** — the real cause is most likely `page.pdf()`'s print-layout pass reflowing slightly taller than the on-screen measurement that produced `captureHeight`, an engine-level measurement/render mismatch, not yet root-caused. **Stopgap in place**: `maxSegmentHeightPx` in `scripts/portfolioCollectionExportPlugin.ts` raised from 3000 to 16000, so most real projects need only 1 segment (segmentCount=1 has no internal auto-pagination, sidestepping the bug class entirely for typical content). Verified against real generated PDFs for both previously-failing projects. **Any project tall enough to still need ≥2 segments (captureHeight > 16000px) remains exposed to this exact bug** — root-cause it before raising `maxSegmentHeightPx` further, since 19200px (200in) is Chromium's real ceiling.
- **`playable-game` and `figma-showcase` templates' actual PDF-capture behavior is an open verification gap**, flagged in `src/lib/pdf/pdfExportRegistry.json`'s `templates` array — not yet read/confirmed in this codebase, do not assume parity with `figma-prototype`'s print-swap pattern.
