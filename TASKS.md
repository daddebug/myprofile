Real repro this session: `project-1ua2677` produced 4 physical PDF segments for 3 planned slices, then (with all projects selected) `interaction-intelligence-system` produced 5 for 4 — confirming this is systemic, not project-specific, and not caused by the `data-project-print`-scoped `figure/table/img` rule previously suspected (that attribute is provably never set during collection capture — its only setter is the owner-only manual print button, gated on a `?printProject=1` query param the collection pipeline never sends). Two CSS-only fixes were tried and both reproduced the identical failure: (a) forcing `break-inside: auto` on figure/table/img under `data-collection-export-capture`, (b) restoring `break-inside: avoid` on every top-level `[data-template-instance-id]`/`[data-document-section]` module (both since reverted/superseded — see `src/styles.css`, "EMERGENCY FIX" comment near `maxSegmentHeightPx`). This means **break-inside CSS is not the actual lever** — the real cause is most likely `page.pdf()`'s print-layout pass reflowing slightly taller than the on-screen measurement that produced `captureHeight`, an engine-level measurement/render mismatch, not yet root-caused. **Stopgap in place**: `maxSegmentHeightPx` in `scripts/portfolioCollectionExportPlugin.ts` raised from 3000 to 16000, so most real projects need only 1 segment (segmentCount=1 has no internal auto-pagination, sidestepping the bug class entirely for typical content). Verified against real generated PDFs for both previously-failing projects. **Any project tall enough to still need ≥2 segments (captureHeight > 16000px) remains exposed to this exact bug** — root-cause it before raising `maxSegmentHeightPx` further, since 19200px (200in) is Chromium's real ceiling.
