- **Collection PDF size: oversized images are now right-sized upstream, inside the capture page, before Chromium prints (2026-08-09).** Root cause was Chromium's `page.pdf()` always embedding a raster `<img>` at its full natural/decoded resolution as raw `/FlateDecode` samples, regardless of on-page CSS display size (never preserves source JPEG encoding, never scales down) — so a source image far larger than its display box balloons the PDF. `scripts/exportImageResize.ts` (new, self-contained, zero-argument — it's serialized via Playwright's `page.evaluate()` and re-executed inside the disposable capture tab, so it cannot close over anything) walks `document.images` after layout has settled, and for any image whose `naturalWidth`/`naturalHeight` meaningfully exceeds its real `getBoundingClientRect()` CSS size (times a 2x retina headroom), redraws it into an offscreen canvas at the capped size (aspect ratio preserved via one uniform scale factor) and swaps `img.src` to that canvas's data URL — pinning the element's CSS `width`/`height` inline first so layout can't shift for intrinsically-sized images, and clearing `srcset`/`sizes` so the browser can't revert to the original resource. Wired into both capture sites: `createExactWebPdf` in `scripts/exactWebExportPlugin.ts` (project pages) and `renderSectionPdf` in `scripts/portfolioCollectionExportPlugin.ts` (cover/section pages), called right after the existing image-load wait and right before `page.pdf()`. Never touches IndexedDB, localStorage, `projects.ts`, `publishedPortfolio.json`, or any published asset — the swap exists only inside that one throwaway page instance. Needs no image-type classification or per-project special-casing, so a future image replacement automatically gets an efficient PDF with no extra work. Verified on the real 3-project Collection PDF regenerated through the live `/export` UI: 87.76MB → 26.41MB (69.9% reduction) from resizing alone; page count (4), page dimensions, and internal cover-tab link annotations byte-identical to the pre-fix baseline; all 4 pages visually inspected with no blur, artifacts, missing images, or layout shift.
- **Final narrow encoding pass closes the remaining gap to the <=10MB target — verified 87.76MB → 5.47MB (93.8% total reduction) (2026-08-09).** After the upstream resize, the remaining size was 100% `FlateDecode` (Chromium's print pipeline never compresses beyond raw deflate-of-samples, regardless of resolution) — a pure encoding-efficiency gap, not an oversizing problem. `scripts/pdfStreamEncodingOptimizer.ts` (called from `mergeCollection` in `scripts/portfolioCollectionExportPlugin.ts`, right after the canonical merge produces literal bytes) fixes this with a rule reverse-engineered from a real Smallpdf-compressed reference export of this same portfolio (user-supplied, ~4.1MB, inspected object-by-object): every image WITHOUT its own `/SMask` gets a fixed-quality (70) DCTDecode/JPEG re-encode, kept only if genuinely smaller than a real PNG-style-predictor lossless re-filter computed alongside it; every image WITH its own `/SMask` (and that SMask object itself) stays lossless-only, re-filtered the same way. This is a single structural fact already in the PDF (does this exact object declare its own alpha channel), not a guessed photo/UI classifier — confirmed by directly tracing reachability of a page-level luminosity soft-mask's own embedded raster in the Smallpdf reference (via ExtGState `/SMask/G`, a different mechanism from per-image `/SMask`) and finding Smallpdf JPEGs that too, exactly matching this document's own 54 luminosity-mask Form XObjects being handled the same way. Every lossless candidate is decoded back and verified byte-for-byte before use; every JPEG candidate is decoded back and dimension-checked. Also deduplicates byte-identical image objects (via a generic ref-graph rewrite + delete, since reassigning what a ref points to doesn't reduce size unless every reference to the old object number is repointed first) and saves with `useObjectStreams` enabled. Verified on the real 3-project Collection PDF, regenerated through the live `/export` UI end to end: 26.41MB → 5.47MB (61 of 125 images recompressed, 47 as JPEG, 10 duplicate objects removed); page count (4), page dimensions, and links byte-identical to the original baseline; all 4 pages visually inspected at both normal and 200dpi zoom (cover gradients still banding-free — the size comparison naturally keeps smooth gradients on the lossless path — dense UI-screenshot text still sharp, 3D scene renders and alpha-having graphics unchanged, no white blocks). ## Publishing architecture

- `src/lib/publishing/publishSourceRegistry.json` is the single machine-readable source registry. Browser export assets carry `sourceAdapterId`; exports from another registry version are rejected.
- `scripts/publishing-preflight-lib.mjs` generates `output/publishing-preflight-manifest.json` with projects/sections, content records, every discovered browser or disk asset, adapter ownership, source/intended paths, byte size, MIME type, and source-level failures.
- Production import runs the same preflight before writes and after path rewriting. Unknown sources, missing configured covers/assets, local/dev paths, and published references without intended output are blocking errors.
- `docs/PUBLISHING_ARCHITECTURE.md` documents the inventory and verification rules. DILIDA DESK sync is paused and must consume this manifest rather than duplicate discovery.
- Playable Game files are discovered and listed; a local build still blocks publishing until it either has a real hosting/import path or is migrated to an external `playUrl` (see "Playable Game: canonical hosted-build architecture" above) — it is never silently omitted.
- **The production URL for this portfolio is `https://myprofile-teal.vercel.app`.** `myprofile.vercel.app` (no `-teal`) belongs to an unrelated third party and must never be used for verification.
- **Project covers publish correctly now** (2026-08-07, commit `8a57564`, verified live). `src/lib/productionBundleExport.ts` collects covers from `content/projects/project-covers.json` (the `project-covers-disk` adapter — the real, currently-used owner-editing path via `ProjectCoverEditor.tsx`), not the long-dead `project-covers-indexeddb` store. A registry row having a real importer implementation does not guarantee it has a real exporter/collector implementation — both ends must be checked when auditing a source family, not just one.
- `import-production-bundle.mjs` supports an explicit `--exclude-project=<id>[,<id>...]` flag for excluding specific projects from one publish run while preserving (not deleting) their existing published state — used when a project has an unrelated, already-known blocker (see Playable Game hosting below). Never a silent default; always logged when used.
- **Production asset integrity gate (2026-08-17).** `scripts/assetIntegrity.mjs` validates every bundle image's decoded bytes against a real image file signature (PNG/JPEG/WEBP/GIF/AVIF/SVG) before it can be treated as collected or trusted as an already-published disk fallback; empty/near-empty/garbage bytes fail closed (`INVALID_ASSET_BYTES`, blocking). A declared-MIME/extension mismatch is recorded as a non-blocking warning only (`ASSET_MIME_MISMATCH`) — real published files legitimately carry a mismatched extension from an earlier compression pass, so this is never treated as corruption. Wired into `buildPublishingPreflight` (both the bundle-image ingestion loop and `resolveAlreadyPublishedProjectBodyAsset`'s disk-fallback resolution), so both the standalone `pnpm portfolio:preflight` and `import-production-bundle.mjs`'s pre-write gates see it — no separate write-time interception exists. The Game Experience report item carries a per-cover `assetIntegrity: { totalCovers, valid, invalid, inherited }` summary so a corrupted cover is never hidden inside one aggregated UNCHANGED/UPDATED line. Exists because a real publish attempt wrote ~3-byte corrupted data into 70 production image files before detection (see `CHANGELOG.md`, `TASKS.md`).
